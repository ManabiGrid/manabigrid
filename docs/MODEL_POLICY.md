# MODEL_POLICY — 新単元制作に使えるAIモデルの方針

新単元の制作貢献に使えるAIモデルの現行リスト・将来の更新手続き・偽装への防御を定めます（貢献の全体像は [CONTRIBUTING.md](../CONTRIBUTING.md)）。

## 1. 現行の受付モデル（2026-10-23時点）

| 用途 | モデル | 条件 |
|---|---|---|
| 新単元の制作（調査→正規化→執筆→セルフQA） | **Claude Fable 5.1**（Anthropic・model id: `claude-fable-5-1`） | reasoning effort medium 以上。サブエージェントを使う場合もすべて Fable 5.1（執筆とセルフQAだけは次の行の Opus 5.5 も可）。2026-09-02 より前に Claude Fable 5（`claude-fable-5`）で制作した成果物はそのまま有効（§3-1・§3-3） |
| 上のうち**執筆とセルフQA**（第2系統） | **Claude Opus 5.5**（Anthropic・model id: `claude-opus-5-5`） | reasoning effort max。調査と正規化は Fable 5.1 で行い、その成果物を受けて執筆する。執筆とセルフQAでサブエージェントを使う場合は Fable 5.1 か Opus 5.5。§3-4 の較正（2026-10-23）で追加 |
| 新単元の制作（**理科で Fable 5系が執筆を拒否した範囲のみ**） | 複数モデルの分担（例外運用） | 一発書き禁止・GPT-6 Astra Pro の批判レビュー組み込み必須。判定手順と条件は §5 |
| 批判レビュー（メンテナ側で実施） | **GPT-6 Astra Pro**（OpenAI） | 制作側と別ベンダであること（共有盲点の排除） |
| 独立検算と条件の点検・直しの反証（メンテナ側で実施） | **GPT-6系の Codex**（OpenAI） | 批判レビューの前に全設問の再計算と主張の成立条件の点検を行い、指摘を直した後に、直しが新しい誤りや条件の抜けを持ち込んでいないかを確かめる。制作側と別ベンダであること |
| 誤り報告・改善・弱点指摘・デザイン・素材提供 | **指定なし** | 人力・どのAIでも歓迎 |

**既存単元の大幅改稿の扱い**: 既存単元の意味変更（説明の論理・例題の設定・数値体系の置き換えなど）が相当範囲に及ぶPRは、入口が「改善」であっても**新単元の制作に相当するとメンテナが判定することがあります**（判定の軸は変更行数ではなく意味の変更範囲）。その場合、上表の「新単元の制作」の条件（受付モデルの要件・工程成果物一式の同梱）を適用します。

**制作4工程の外の工程**: 図版生成スクリプトの作成、検算や批判レビューの指摘の最小差分の適用、初見読者検査の実施、批判レビューの依頼文の組成、表記の機械的な検査と修正は、上表の対象外です（モデルの指定はありません）。ただし本文を書き換える工程は、変更が「採否を裁定した指摘の最小差分」に留まることを来歴（置換の本数・変更したファイルの数）で示します。メンテナ側で行う指摘の採否と最終の判定は Fable 5.1 が行います。意味の変更範囲が相当に及ぶ場合は上の「大幅改稿の扱い」に従います。

## 2. なぜモデルを限定するのか（基準は銘柄ではなく実力）

限定の本質は「Anthropic 製だから」ではありません。基準は次の2つです。

1. **ゼロイチの開拓力**: 工程の途中で、既存の定石にない解決策（検証装置・様式・構造）を自分から設計できること。この教材の品質装置はその産物であり、単に指示に従うだけのモデルでは同水準の単元になりません（実例は [METHODOLOGY.md](METHODOLOGY.md)「なぜ Fable 5系なのか」）。
2. **検証系との較正**: 本プロジェクトのセルフQA契約・批判レビュー（GPT-6 Astra Pro）・人間レビューは、Fable 5系の出力水準を前提に調整されています（Fable 5→5.1 の移行時の較正確認は §3-1 の補則）。前提が違うモデルの出力は、検証系が正しく機能しません。

## 3. 将来のモデル更新手続き

### 3-1. Fable 5 の後継（アップグレード版）が出たとき

後継モデル（例: Fable 系の次版）は自動的には受付リストに入れず、次の**較正テスト**を経て追加します:

1. メンテナが既存の較正済み単元1本ぶんのプロンプトを後継モデルで再実行する
2. 出力を GPT-6 Astra Pro（またはその時点の別ベンダ最上位）による批判レビューにかけ、既存水準と比較する
3. 人間（メンテナ）が採否を裁定し、本ファイルの表を更新して履歴に残す

追加後も旧モデル（Fable 5）製の既存教材はそのまま有効です——各教材の来歴に使用モデルが記録されており、遡って無効にはしません。

**運用上の補則（2026-09-02追加）**: 後継モデルが Claude Code の既定モデルとなり、旧版が通常の制作環境で使えなくなった場合は、較正テストの完了を待たずに後継を受付リストへ入れ、**最初の後継製単元1本を較正テストの対象**として結果を §3-3 に追記する（制作が止まる期間を作らないため）。Fable 5→Fable 5.1 の移行で初めて適用した。

### 3-2. 他社から同水準のモデルが出たとき（較正プロトコル）

他社モデルも、次の較正プロトコルを通れば受付リストに入りえます。判断基準は §2 の2点（ゼロイチの開拓力・検証系との較正）であり、特定ベンダの囲い込みが目的ではありません。また、受付モデルが1系統しかない状態は、そのモデルの障害・利用制限が制作の停止に直結するため、**同水準の第二モデルの認定は制作継続性の観点でもプロジェクトの利益**と考えます。

**較正プロトコル（他社モデル版）**:

1. **パイロット単元の完走**: 候補モデルで、未着手単元1本を正規パイプライン（調査→正規化→執筆→セルフQA）どおりに完走する。工程成果物一式（調査ノート・執筆用要約・QA記録）の同梱は必須。推論設定（reasoning・温度等の相当設定）を申告する
2. **別ベンダによる批判レビュー**: 制作に使った候補モデルと**別ベンダ**のレビューモデルで批判レビューを実施する（制作側と批判側が同一ベンダにならない原則は常に維持）
3. **ベースライン比較**: 較正済みの既存単元（Fable 5製）と、指摘の質・量、誤りの混入率、様式の遵守、検証装置の自発的考案の有無を比較する
4. **人間レビュー**: メンテナが通読・検収し、「既存水準以上」と裁定できた場合のみ受付リストへ追加する
5. **固有事項の確認**: 次を確認し、結果を履歴表に記す——(a) 出力の利用条件が教材ライセンス（CC BY 4.0）と整合すること (b) 安全機構の差（執筆できない領域の有無・理科§5と同様の機械判定） (c) モデルのバージョン固定可能性（重み固定できるモデルは再現検証の観点でむしろ有利）
6. **記録**: 追加・不採用のいずれも、判断日・較正結果の要旨を §3-3 の履歴に残す

較正テストの実施はメンテナの判断で行います（候補の申し出は Issue で受け付けますが、テスト実施を約束するものではありません）。

### 3-4. 同じ会社の別系統のモデルを第2系統に加えるとき（較正プロトコル・同社版）

受付モデルと同じ会社の別系統のモデル（例: Claude Opus 5.5）は、§3-1（後継）にも §3-2（他社）にも当たらないため、次を通してから受付表に**第2系統**として加えます。趣旨は §3-2 と同じです（受付モデルが1系統だけの状態は、そのモデルの障害や利用制限が制作の停止に直結するため）。

1. **パイロット単元の完走**: 候補モデルで未着手単元1本を正規パイプラインどおり完走する。受付モデルと分担した工程と、推論設定を申告する。工程成果物一式を同梱する
2. **受付モデルによる独立の点検**: 候補モデルの QA 記録を見せずに、受付モデル（Fable 5.1）が同じ単元を点検し、2つの点検の指摘の重なりを記録する
3. **別ベンダによる検算と批判レビュー**: GPT-6系の Codex による全設問の再計算と条件の点検と、GPT-6 Astra Pro による批判レビューを行う
4. **基線比較**: 同じ時期に同じ工程と同じ規模の批判レビューを受けた受付モデル製の単元と比べる。比べる量は、批判レビューで採用した指摘（本文と解答）のレッスンあたりの件数と、読者の答えが変わる誤りの件数。合格の線は比べる前にメンテナが決める
5. **メンテナの裁定**: メンテナが比較の結果を見て採否を裁定し、受付表に加える範囲（工程・推論設定・サブエージェントの扱い）を書く
6. **記録**: 追加・不採用のいずれも §3-3 の履歴に判断日と結果の要旨を残す。パイロット単元は、裁定が「追加」のときだけ公開へ進む

## 4. モデル偽装への防御（正直な設計）

「Fable 5.1 と申告して別モデルで作る」貢献を完全に技術的に見破る方法は、現状存在しません。そのうえで、次の多層防御を敷きます。

1. **工程成果物の必須化**: 調査ノート・執筆用要約・QA記録の一式がないPRは審査に入りません。これらは正規パイプラインの自然な副産物で、後から偽造するには本体を書くのと同等以上の手間がかかります。
2. **成果物の整合審査**: 調査ノートと要約の対応、QA記録の検算をメンテナ側で再実行し、つじつまを機械的に確認します。
3. **抜き打ち再現**: 疑義がある場合、プロンプトの一部をメンテナ側の Fable 5.1 で再実行し、水準・挙動を比較します。
4. **最終網**: すべての新単元は GPT-6 Astra Pro の批判レビューと人間レビューを通過するまで「ドラフト」表示のままです。低品質な貢献がマージだけで「完成教材」として世に出ることはありません。
5. **ペナルティ**: 虚偽申告が判明した貢献は取り込まず、以後の同一貢献者の単元PRはお断りすることがあります（[CONTRIBUTING.md](../CONTRIBUTING.md)）。
6. **来歴の書き方**: 工程成果物の冒頭の「実行モデル」には、制作を指揮した側が指定したモデル名を書き、実行環境の記録（ログ）で照合します。生成した側のモデルの自己申告だけを来歴にしません。

**受付モデル（§1）を使えないが執筆で貢献したい人へ**: それは排除ではありません。あなたの知見は**素材の貢献**（誤答パターン・つまずき事例・例題アイデアの提供——モデル不問・Issueで受付）としてパイプラインの入力になり、教材の品質に直接反映されます。制限を偽装で越えるのではなく、この経路を使ってください。詳細は CONTRIBUTING.md の「素材・知見の提供」。

## 5. 理科の例外——Fable 5系が執筆を拒否する範囲の扱い（追加日は §3-3 の履歴表を参照）

**正直な現状**: 制作の正本モデル Claude Fable 5系には生命科学分野の安全機構があり、該当範囲の執筆プロンプトを渡すとセッションが停止します。**2026-07-16に理科全145単元を機械判定した実測**（Fable 5・当時の分類器）では、停止（fable_blocked）は37単元で、**生物・生態系・環境分野（中学の生物系全単元・生物基礎14/14）と生命史を扱う地学2単元に集中**し、物理・化学は全単元通過でした。単元ごとの判定は[理科レジストリ](../curriculum/registry/science.md)の備考欄に公開しています。判定は時点・モデルつきの記録であり、モデル側の更新（2026-08-07 の分類器改善・2026-09 の Fable 5.1）後の再判定は順次行い、備考欄に判定モデルを併記します。この事実は隠さず、扱いを次のとおり定めます。

### 5-1. 例外の成立条件（拒否判定は機械的に行う）

§1 の受付モデル以外での新単元制作を受け入れるのは、**その単元について Fable 5.1 が執筆を拒否したと判定された場合のみ**です。判定手順:

1. Claude Code の「フラグ検知時にモデルを切り替える」設定をオフにする（自動フォールバックを止め、停止をそのまま観測できるようにする）
2. 該当単元の執筆プロンプトを Fable 5.1 に投入する。プロンプトは**停止を引き起こしやすい要素（単元スコープと扱う内容の明示）を冒頭に置く構成**とし、執筆が進んでからの途中停止を避ける
3. セッションの一時停止が発生したら「拒否」、完走したら「Fable 5.1 で制作可能」（=例外不成立・通常ルールを適用）
4. 判定の時点では他モデルへのフォールバック実行を行わない（判定と執筆を混ぜない）
5. 判定結果は単元ごとに記録し、レジストリ／進捗一覧の注記に反映する

**判定は誰が行うか**: 原則として**メンテナ側が事前に実施し、理科レジストリの備考欄に `fable_ok` / `fable_blocked` を記録**していきます（貢献者が着手してから停止に遭遇する無駄を避けるため）。**備考欄が空の単元は判定前**です——着手したい場合は着手宣言Issueで判定を依頼してください。貢献者自身の環境での試行結果も報告歓迎ですが、正式な記録は上記の標準手順による再現確認を経て更新します。

**「後から Fable 5.1 でも執筆できた」という報告について**: 安全機構の挙動はプロンプト構成やモデル更新によって変わりうるため、`fable_blocked` の判定は**恒久ではなく時点つきの記録**です。次のとおり扱います。

- 正当な理由による通過（プロンプト構成の改善・モデル側の更新など）: **歓迎**。メンテナが標準手順で**再現確認したうえで** `fable_ok` へ更新し、確認日を記録します
- **安全機構の意図的な回避（いわゆる脱獄・ガードレール外し）によって「書けた」もの: 受け入れません**。安全機構を欺いて生成された教材本文は、判定結果にかかわらず取り込みません。これは品質の問題ではなく、このプロジェクトの信頼の一線です

### 5-2. 拒否された単元の制作条件（複数モデル必須・一発書き禁止）

- **1つのLLMによる一発書き上げは受け付けません。**
- 必ず**複数のモデルで執筆・批判・改稿を分担**し、かつ **GPT-6 Astra Pro の批判レビューを工程に組み込む**こと。
- 参考構成（メンテナ環境での標準）: 執筆=GPT-6系（Codex）／批判・改稿=Claude Opus（Fable 5系の作業規範を移植したスキルを併用）／反証=GPT-6 Astra Pro（ブラウザ）／統合ののち人間レビュー。
- 工程成果物一式の同梱（§4-1）は例外単元にも同様に必須です。
- **分担の実行ログも工程成果物に含めます**: 例外ルートでは、どのモデルがどの成果物を作り、何をどの順で受け渡したか（各工程の担当モデル・入出力ファイル・実施日）を記録した**分担実行ログの同梱を必須**とします。メンテナはこのログと成果物の整合審査を行い、通常ルートと同じ最終網（§4の抜き打ち再現・GPT-6 Astra Pro 批判レビュー＋人間レビュー）を適用します。単一モデルの一発書きを「分担した」と申告する偽装は、この整合審査と最終網で検出対象になります。
- **GPT-6 Astra Pro 批判レビューの実施主体**: 「工程内で貢献者が実施」または「メンテナ側で実施（PRでその旨を申告すれば可）」の**どちらでも受け入れ条件を満たします**（Pro の契約がない貢献者もこのルートを使えます。通常ルートとの負担差をなくすためです）。
- **証拠の記入先**: 例外ルートのPRでは、PRテンプレートの「理科 fable_blocked 単元の証拠欄」に、拒否判定の確認・各モデルの役割と実行ログ・GPT-6 Astra Pro 反証レビューの成果物（artifact）・工程間の受け渡し記録を記入してください。**証拠欄の記入がない例外PRは審査に入りません。**
